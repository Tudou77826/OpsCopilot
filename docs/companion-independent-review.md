# 伙伴功能独立质量审查

审查日期：2026-10-12。审查对象为当前正式 v5 角色包、v2 奖章包、桌面伙伴助手与伙伴设置，以及相关成长、奖章、排名、人设代码。

## 判断

核心业务框架较完整，已有实际成长结算、八类功能统计、组织排名、成员资料和人设设置。表现层可以运行，但还没有达到细腻、稳定的成品质量。最明显的差距是正式素材存在裁切和杂片，走动缺少姿态与位移的衔接；助手界面看起来能连续聊天，实际请求却不携带前文。

功能数量和质量需要分别验收。七个角色、七组动作、三种阶段和八类奖章均有实现，不代表各帧的轮廓完整、步态自然、角色身份一致或问答体验完整。现有门禁对格式和运行条件覆盖较好，对这些质量问题覆盖不足。

本次没有修改实现、业务记录、伙伴外观、人设、展示选择或排名参与状态，也没有重启服务或操作用户已有浏览器标签。

## 证据范围

- 在独立 Edge 浏览器上下文访问 34115，连续观察当前苔团约 115 秒，采样动作、帧号、位置和朝向。查看伙伴设置与真实排名。页面无异常，审查前后伙伴存档相同。
- 独立生成全部七种正式角色的待机、环顾、舒展、走动八帧联系图和各动作首帧对照图。这些是素材预览，不是逐一切换七个角色后的产品实测。
- 对正式 PNG 检查可见边界、下半身中心和不相连的小组件；对照原稿、标准化代码、播放代码、请求接口和门禁。重新执行素材门禁，全部通过。
- 没有产生新的成长或奖章记录，没有重新执行完整业务测试。业务结算与同步完整度判断来自现有实现和验收材料，不能替代新的写入回归。
- 本地模型端点不可用；本次没有验证真实模型回答质量。以下有关对话上下文和名称的发现来自请求链路，不是根据模型连接失败推断功能故障。

证据目录：[独立审查记录](../e2e/.runtime/independent-companion-review/)。其中 `observation.json` 保存采样和存档对照，`frame-metrics.json` 保存素材检查结果，`inspect.mjs` 与 `analyse.mjs` 可复现上述检查。

## 优先发现

### 1. P1：微光舒展素材已经裁断耳朵，且含邻帧碎片

**确认缺陷。** 查看 `lumen-v5/lumen-stretch-3.png`、`lumen-stretch-4.png`，宽耳的外端呈明显平切，边上还有与主体不相连的紫色片段。联系图中的第 3、4 帧尤其清楚：[舒展联系图](../e2e/.runtime/independent-companion-review/assets-stretch.png)。原稿 `art/companion/roster-v3/lumen-source.png` 的宽耳姿态跨过相邻格子的边界，自动划分没有可靠分离这些角色。

定位：`tools/pixel/atlas.mjs:2`、`:22` 按最低 Alpha 投影切缝；`tools/pixel/build-roster-ambient.mjs:28` 将切出的区域直接变为正式帧。后续缩放留白无法修复已经被切掉的耳端。

影响：自动舒展时角色轮廓突然断裂。增加帧数或优化播放器不能解决这个问题。

修复：重新生成留有明确间距、完整轮廓的相关姿态；必要时给角色包提供人工确认的区域，而不是对所有原稿依赖自动切缝。不要通过隐藏两帧宣称舒展完成。

验收：微光完整舒展、循环衔接和当前展示尺寸均无平切耳端、邻帧残片。正式原稿与输出帧必须逐一对照确认。

### 2. P1：三种角色的招呼帧顶部残留细线杂片

**确认缺陷。** 赤尾、浪豆、知羽的招呼帧包含顶部悬空的细小线段。[动作首帧对照](../e2e/.runtime/independent-companion-review/assets-transition.png) 可见这些不属于角色的碎片。赤尾 `greet-0` 在 y=20 有 21、18、17 像素的三个不透明组件，主体从 y=42 才开始；全部八个招呼帧均检测到同类顶部组件。浪豆和知羽八个招呼帧也检测到顶部组件。

定位：`tools/pixel/build-roster-motion.mjs:14` 使用等宽原稿格子；`tools/pixel/sheet.mjs:25` 的远端组件剔除只在传入 `region` 时启用。v5 继续复用了这些 v4 互动帧（`tools/pixel/build-roster-ambient.mjs:24`）。

影响：招呼时头顶忽然出现横线或异物；深色背景和大幅展示使它们更明显。

修复：复查基础互动原稿的切片区域，移除明确属于邻行的碎片，并保留真实装饰物和柔边。不能仅提高统一面积阈值，以免删除微光星光等合法细节。

验收：七角色基础互动帧在浅、深背景和实际尺寸下无杂片；组件检查应支持允许的装饰清单，异常组件需要人工确认。

### 3. P1：走动已有迈步素材，但衔接仍像整体平移

**产品体验不足，兼有明确的播放设计原因。** 当前苔团实际向右约 60 像素/2.5 秒，此后约 120 像素/5 秒往返。位移确实发生，帧也在变化；不能把它描述成只有静态图片移动。不过，起步直接换成侧面步态，停步立即回正面，向左通过镜像翻转，没有转身、起步或收步的过程。

定位：`SceneCompanion.tsx:57` 直接设置朝向，`:64` 完成后立即恢复正面，`:69` 使用线性整体位移。`ambientMotion.ts:10` 按距离计算时长并夹在 1.6–5 秒；素材固定每帧 140 ms（`build-roster-ambient.mjs:49`），没有脚接地相位和每周期步幅数据。停下的时刻因此也不与步态收尾对齐。

影响：角色有脚步，但脚与地面的关系不足，边缘停下及左右换向容易突变。七种角色动作数量相同，实际步态完成度不一致。

修复：给每种角色定义步幅与接地相位；位移距离与步态周期一致，在接地或双脚稳定帧结束。增加短转身、起步与停步姿态，并保留停下后的朝向，再自然回看用户。采用合成位移可以继续保留性能优势。

验收：所有七种角色均审看两次完整往返、步态循环接缝、行走中点击和窄窗口。停止时无突然换脸，支撑脚没有明显反向滑动，边界不裁切，减少动态效果与暂停仍有效。

### 4. P1：多轮聊天只存在于界面，模型请求没有前文

**代码确认的功能缺口；真实模型效果未实测。** `AIChatPanel.tsx:38` 保存多条消息并展示“新建对话”，但 `:92` 调用的是 `runtime.ask(question)`。`frontend-shell/src/assistant/runtime.ts:8` 和 `wailsAssistantRuntime.ts:8` 也只接受当前问题；`pkg/ai/agent.go:197` 每次创建新的 system 消息，再只追加当前 user 问题。没有把此前对话送入模型的路径。

复现条件：先给出故障现象或要求，再问“按刚才那个方案继续”或“第二步是什么意思”。界面保留前文，模型却没有收到它。

影响：伙伴作为持续 AI 入口时，用户对连续问答的预期无法成立。这个缺口不需要等待 ACP 才能修复。

修复：在助手适配接口加入会话与有界历史；后端明确处理上下文预算、取消和会话隔离。“新建对话”需清空请求上下文，而不只是清空展示。

验收：请求捕获应证实第二轮含所需前文，新会话不含旧历史；再用可用模型完成实际追问。不能仅用返回固定文本的组件测试验收连续对话。

### 5. P2：默认人设不知道伙伴的自定义名称

**代码确认的身份缺口；实际回答未实测。** 当前存档物种为 moss，名称为“本地微光二号”。`app_assistant.go:29` 只调用 `companion.PersonaFor(snapshot.Pet.SpeciesID)`，而 `species.json:4` 的文本是“你是苔团”。当前名称没有进入请求链路。

影响：用户问伙伴叫什么时，界面身份和模型可见身份可能不一致。自定义人设可能另写名字，但不能要求一般用户手动补齐系统已有的事实。

修复：将名称、类型等身份事实与表达风格分开传入。用户文本主要控制表达；系统应明确目前展示的伙伴身份。不要把经验、排名或业务内容未经授权一并塞入提示词。

验收：重命名、切换物种以及自定义风格后，捕获请求中的身份均与界面一致；使用可用模型验证身份问答。

### 6. P1：现有验收能证明资源可播放，不能证明素材质量

**确认的验收盲点。** 上述裁切与杂片存在时，重新执行 `node tools/checks/check-companion-assets.mjs` 仍全部通过。门禁检查尺寸、留白、透明度、数量、声明的锚点和时序，没有检查角色是否在原稿切片时已被裁断，也没有识别异常孤立组件。

`e2e/harness/companion-ambient-review.mjs:10–12` 以按钮包围盒 x 不变判断待机稳定，不能发现 PNG 内人物漂移。`:20`、`:22` 以位移大于 8 像素和图片 URL 改变判断行走，不能证明步态自然。`SceneCompanion.test.tsx:5` 用模拟图片和动画替代正式帧，适合验证生命周期，不能用于美术质量结论。

修复：保留格式和生命周期门禁，补充正式素材的视觉验收。自动检查可见脚底、主体中心、异常组件、帧间比例变化和原稿边界；所有角色需要动作联系图、循环录屏和明确的人工通过记录。量化检查对转头、跳跃和装饰物分别设定合理规则，避免盲目对齐抹掉真实动作。

验收：用已确认的裁断耳朵、顶部线段和人物在固定画布中移动作为回归样本；新检查能阻止它们被标记为质量通过。报告分别写“格式通过”“运行通过”“视觉通过”。

### 7. P2：成长阶段成立，但视觉成长表达很薄

**产品体验不足，不是存储故障。** 三个阶段共用完全相同的动作和形象，只有 `160/216`、`188/216`、`1` 三种缩放。定位：`tools/pixel/build-roster-motion.mjs:42` 与各 v5 manifest 的 `stageScale`。成长结算和阶段标签存在，但视觉上主要表现为变大。

影响：养成的阶段变化缺少可辨认的里程碑；七种角色已有性格文本，行为调度却全部按 `look → stretch → walk` 固定轮换（`SceneCompanion.tsx:53`），长期观看仍显得统一、重复。

修复：在保持现有数据结构的前提下，先建立可识别的阶段变化，例如一个可解锁的装饰、姿态或小动作；给不同角色配置动作权重与停留节奏。无需马上扩展复杂养成系统，也无需增加社交互动。

验收：去掉阶段文字时，用户仍能区分三个成长阶段；连续观察一分钟能感到角色行为差异。新动作按需加载，静态与减少动态效果场景保持可用。

## 修复顺序

先修正式素材的裁切和杂片，同时建立能拦住这些问题的质量检查；随后修复转身、步幅与收步，逐个审看七种角色的往返和互动衔接。助手的历史与身份应作为功能完整度问题单独完成，再精进成长阶段和性格差异。

下一次交付应提供同一版本的正式资源联系图、七角色实际播放证据、对话请求证据与有界性能记录。不能再用帧数、测试总数或一次 URL 变化概括“质量已完成”。
