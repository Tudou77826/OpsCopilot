# 养成系统呈现架构：固定属性 × 可定制呈现

> 状态：设计稿（架构层），供评审
> 关联文档：[花园系统设计](garden-design.md)（行为、成长、闪光、防刷与数据边界沿用其结论）、[主题与皮肤设计](theme-design.md)
> 本文回答一个问题：**养成属性是固定的，但呈现方式要支持植物/动物/建筑等任意题材、像素/字符/图片等任意画法，架构怎么分层。**

## 1. 一句话架构

```
┌───────────────┐   只读    ┌─────────────────┐
│  成长状态层    │──────────▶│    呈现层        │
│ （固定属性）   │           │ （可插拔皮肤包）  │
└───────────────┘           └─────────────────┘
     Go 后端                     前端渲染
   唯一事实来源                任何画法都行
```

**核心规则只有一条：呈现层是状态的纯函数。** 后端只认识"属性 + 数值 + 事件"，永远不知道"植物"或"像素"的存在；前端拿到同一份状态 JSON，交给哪个呈现包，就长成什么样子。换呈现包 = 换皮，属性、等级、里程碑一个不动。

这和主题系统的结论同构：**主题/皮肤管颜色和形状的"来源"，养成呈现管"题材与画法"**——两者互不干涉，花园面板内永远是呈现包自己的视觉体系（garden-design.md §4 的结论继续成立）。

## 2. 固定属性（后端唯一事实来源）

属性集合是**封闭**的，写在代码里，呈现包不能增删——否则第三方的呈现包会反过来要求后端改数据结构，边界就破了。

### 2.1 个体属性（每株/每只/每座）

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `speciesId` | string | 物种（固定目录，见 2.3） |
| `instanceId` | string | 实例标识（同物种可有多个实例） |
| `level` | 1–30 | 等级 |
| `stage` | 0–5 | 六个形态阶段：发芽/幼苗/分枝/繁茂/开花/成熟（每 5 级一阶） |
| `xp` / `xpToNext` | number | 当前成长值 |
| `shiny` | bool | 闪光品质（纯收藏，无数值差异） |
| `acquiredAt` / `days` / `lastGrewAt` | time | 获得时间、成长天数、最近成长 |
| `milestones` | [] | 里程碑（首次复用、第 100 次传输…） |
| `slotId` | string | 摆放位置（用户可整理） |

### 2.2 全局属性（花园）

花园等级、已解锁地块、物种图鉴（发现过哪些物种）、保底进度、规则版本 `ruleVersion` 与数据版本 `schemaVersion`（garden-design.md §12 沿用）。

### 2.3 物种目录（固定的"位"）

物种目录与呈现解耦的关键：目录里只有**语义位**，没有形象。

```
speciesId        领域          语义
session-tree    连接与会话     稳定连接、持续值守
cmd-mint        快捷命令       重复工作变轻巧
script-vine     脚本自动化     自动化延展
transfer-fern   文件传输       信息安全流动
guard-orchid    安全治理       克制与边界
knowledge-tree  诊断与知识     经验沉淀
```

`speciesId` 是稳定的、永不变更的标识（可以改展示名，不能改 id——呈现包靠它对应形象）。新行为领域 = 目录加一个语义位，呈现包各自决定把它画成什么。

## 3. 状态快照（两层之间唯一的接口）

后端暴露一个只读快照，形如：

```jsonc
{
  "schemaVersion": 1,
  "ruleVersion": 1,
  "garden": { "level": 3, "unlockedPlots": ["central", "connect", "quickcmd"] },
  "specimens": [
    {
      "speciesId": "cmd-mint", "instanceId": "i_01H…",
      "level": 7, "stage": 1, "xp": 340, "xpToNext": 120,
      "shiny": false, "acquiredAt": "…", "days": 12, "lastGrewAt": "…",
      "milestones": [{"id": "first-reuse", "at": "…"}],
      "slotId": "central:3"
    }
  ],
  "pity": { "sinceShiny": 12 },
  "pending": []            // 未领取的发现/升级（garden-design.md §10 的三级反馈）
}
```

约束：

- **无呈现语义**。没有"叶子数""楼层数""调色板"这类字段——那是呈现包从 `level/stage` 推导的；
- **纯函数可渲染**。呈现包拿到快照 + 本地时钟，即可确定性画出全部内容，不依赖任何会话外的隐藏状态；
- **版本协商**。快照带 `schemaVersion`；呈现包声明自己支持的版本区间，不匹配时前端显示"呈现包与数据版本不符"，而不是渲染出错误形象。

## 4. 呈现包（可定制的"皮"）

### 4.1 包的结构

一个呈现包是一个**静态目录**（首版随应用内置，不开放远程下载——避免供应链问题；本地自制包放用户数据目录）：

```
gardenpack.json        清单：id、名称、作者、schemaVersion 区间、画法类型、资源索引
assets/…               形象资源（按画法类型，见 4.2）
theme.css              可选：该包的少量局部样式（限 --garden-* 前缀的变量）
```

清单里每个物种声明资源索引：

```jsonc
{
  "id": "pixel-garden",
  "name": "像素花园",
  "art": "pixel",                    // pixel | glyph | svg | image
  "schemaVersions": "1",
  "species": {
    "cmd-mint":  { "sheet": "plants.png", "frame": { "cols": 6, "rows": 6 } },
    "session-tree": { "sheet": "trees.png", "frame": { "cols": 6, "rows": 6 } }
  }
}
```

### 4.2 四种画法（第一版全部内建，同一套状态接口）

| 画法 | 资源 | 寻址方式 | 适用 |
| --- | --- | --- | --- |
| `pixel` | 一张精灵表 | `stage × 6 + level 段` 选帧；闪烁用帧偏移 | 最常见的定制需求，成本最低 |
| `glyph` | 字符集映射 | `stage` → 字符串数组，`level` 段选择，颜色走花园固定色板 | 零美术资源，纯文本即可做一个包（`|`, `v`, `T`…），也天然支持终端风 |
| `svg` | 参数化分层 SVG | 按 `stage` 开合图层、按 `level` 微调（garden-design.md §16.1 建议的参数化分层模型） | 官方默认包，150 个视觉状态用图层组合表达 |
| `image` | 每阶段一张图 | `species/stage-{0..5}.png` | 有整图素材的人 |

四种画法共享同一个**选择函数**：`(speciesId, stage, level, shiny) → 资源引用`。包内可以混合（比如主体 SVG + 成熟期贴图），由清单声明。

### 4.3 题材无关

架构上不存在"植物包""建筑包"的区别——**题材就是资源内容，不是代码**。建筑包把 6 个阶段画成地基→封顶→落成，动物包画成蛋→幼年→成年，走的都是同一份清单格式。判定一个包合法的依据只有：清单可解析、`art` 类型内建、资源齐全、版本匹配。

### 4.4 呈现包与主题/皮肤的关系

- 花园呈现包**不受**工作台主题/皮肤影响（garden-design.md §4）：它的色板随包自带，亮暗两模式下同一套（仅允许包声明一处例外——面板外框的接缝色可以读 `var(--bg-secondary)` 之类，使接缝不突兀）；
- 与 UI 皮肤（原版/Windows/Teams）零耦合：换皮肤不换花园长相。

## 5. 各层落点（沿用仓库既有约定）

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 状态层 | Go：`pkg/garden`（新） | 事件结算、等级/阶段计算、保底、持久化（沿用 `internal/atomicfile`/`filetxn`）、快照 RPC（sidecar 加 `shell.garden.snapshot` / `shell.garden.claim` 等少量方法） |
| 事件源 | 既有业务路径 | 事件只在后端可验证的结果处产生（连接建立、传输完成、脚本回放结束…），前台不上报（garden-design.md §6 的两条路径中**选定前者**） |
| 呈现运行时 | `frontend-shell/src/ui/garden/`（新） | 加载呈现包、选择函数、渲染循环、详情抽屉、发现反馈；桌面与 Teams 共用 |
| 内置呈现包 | `frontend-shell/src/ui/garden/packs/` | 首发两个：`flora-svg`（参数化分层 SVG，官方默认）与 `pixel-garden`（精灵表示例，兼作第三方格式文档） |
| 宿主 | 桌面 / Teams 插件 | 只提供停靠槽位（与快捷命令共用，garden-design.md §5.2），不含任何花园逻辑 |

呈现运行时对包的加载是**同步、纯数据**的（JSON + 静态资源），不执行包内任何脚本——`theme.css` 之外不允许可执行内容，这是定制能力的安全边界。

## 6. 关键设计取舍（为什么这样分）

1. **属性固定、呈现开放**，是这套架构的全部意义。属性一旦开放给呈现包定义，"换皮不换数据"就不成立；呈现一旦被后端理解（比如后端存"叶子数"），多画法就不成立。这条线画在"状态快照"上。
2. **`speciesId` 稳定 + 资源索引在包里**，让"加一个物种"和"加一个包"变成两个独立动作：目录加语义位（后端）、各包自己补形象（内容），互不阻塞。
3. **`stage` 与 `level` 分开**，是因为呈现的真实成本在"明显变化的形态"（6 档），而"成长的连续感"由等级内的微变化表达。像素/图片画法可以只出 6×N 帧，SVG 画法用图层，glyph 画法用字符串——同一语义，各画法按成本自选表达密度。
4. **`shiny` 是独立布尔**而不是另一套资源：各画法自己决定闪光的表达（像素包加微光帧、glyph 加色反相、SVG 加滤镜层），但状态里只有一个 bit，保底与概率逻辑完全不感知画法。
5. **首版只内置、不开放下载**：定制能力的验证由自带的 `pixel-garden` 示例包承担——它能跑通，格式就是文档。

## 7. 分阶段落地

1. **阶段一（状态层 + SVG 默认包）**：`pkg/garden` 状态机 + 快照 RPC + `flora-svg` 参数化包 + 停靠面板。验收沿用 garden-design.md §14.1（事件结算、防刷、重启一致）。
2. **阶段二（多画法）**：呈现运行时支持 `pixel`/`glyph`/`image`，内置 `pixel-garden` 示例包；验证"同一份快照，三种画法渲染一致的状态语义"。
3. **阶段三（本地自制包）**：用户数据目录的包加载入口 + 格式文档（以 `pixel-garden` 为范本）+ 校验失败的用户可见错误。

## 8. 待确认

1. 首发内置包是否就按"参数化 SVG（默认）+ 像素（示例）"两个走（本文建议）；字符画是否首版就要（成本最低，但需要定字符色板）。
2. 事件源范围首版先接哪几个：建议先"连接建立 + 文件传输完成 + 脚本回放结束"三个后端可验证点，快捷命令复用等待终端回显可用后再接（garden-design.md §6 的硬约束）。
3. 呈现包是否允许声明"多物种共享一张精灵表"（省资源但清单稍复杂）；本文暂按每物种独立资源走。
4. 快照 RPC 的拉取节奏：建议打开面板时拉一次 + 领取/升级时增量推，不做后台轮询（花园不在前台时不产生任何流量）。
